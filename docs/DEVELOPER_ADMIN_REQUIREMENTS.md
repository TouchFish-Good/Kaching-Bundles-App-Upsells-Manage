# Developer Admin Console 需求文档（阶段 1，待确认）

更新日期：2026-10-14。状态：阶段 1 已获确认；具体实现方案仍须分阶段确认。

## 1. 背景与目标

目标是让应用开发者及获授权的内部管理员，在一个独立入口确认商家安装状态、查询本应用的活动、定位故障，并追溯内部管理操作。它不是 SHOPLINE 商家端，也不应以商家会话授权内部人员跨店访问。首版成功标准：能可信地回答“哪些店铺安装了应用、某店有哪些真实活动、当前服务是否异常、谁查看或执行了敏感操作”。现有应用仍处于原型与基础接入阶段，部分问题暂时没有真实数据可回答。

业务边界：仅管理本应用有权处理的数据；不把 SHOPLINE 平台所有商家、所有优惠活动或全平台运行状态解释为本应用可见范围。

## 2. 已核查的项目事实

商家应用位于桌面 `Kaching Bundles App & Upsells New/bundles-app-upsells-new`；本管理后台目标目录目前为空。商家应用有 `app/` Express 服务、`web/` React 前端、`product-discount-customizations/` Function、`theme-app-extension/` 和 `docs/`。`app/src/shopline.ts` 使用 SQLite 会话存储；数据库当前仅有 `shopline_sessions(id, handle, state, isOnline, expires, scope, accessToken)`。授权成功后注册 Webhook，卸载 Webhook 删除会话。现有 `/api/*` 走商家会话验证，不能直接充当管理员鉴权。`web/src/pages/quantity-breaks.tsx` 从 `web/src/prototype/data.ts` 初始化活动并保存在组件状态，现有活动及统计不是跨商家的持久化业务记录。`app/src/controller/product/create.ts` 为示例商品创建接口。`shopline.app.toml` 当前声明 `write_products` 权限；不能据此推断优惠读取、分析或扩展状态 API 已获授权。`docs/APP_PROGRESS.md` 也标注真实数据持久化、Function/主题和结账验证尚未完成。

风险提示：当前 Webhook 处理会记录完整 payload，并把认证结果作为响应数据返回；服务端还存在带商家 token 的会话表。阶段 2 必须先审查日志脱敏、会话访问边界和该响应行为，不能将这些原始值展示到管理后台。

## 3. 用户角色与权限边界

候选角色：Owner（配置管理员和查看审计）、Operator（跨店只读排障及查看经脱敏日志）、Viewer（概览与只读商家/活动信息）。首版默认全部业务页面只读；任何重试 Webhook、重装扩展、修改活动、导出原始数据等写操作均不纳入 MVP。具体角色分配人、身份提供方和是否需要双人审批待确认。普通商家账号没有后台入口或管理员 API 权限。访问单个店铺须按稳定 store ID 关联；只凭域名或 handle 不足以作为永久身份键。

## 4. 范围与优先级

MVP：内部管理员登录与服务端授权、商家安装清单及详情、可用数据范围内的只读 Bundle 查询、基础 Overview、有限的已采集错误事件、访问审计。若真实 Bundle 持久化数据尚不存在，活动页应清晰显示“数据源未接入”，不得使用前端样本充当真实活动。

P1：结构化 API/Webhook/业务日志检索、服务健康与任务监控、Function/Theme Extension 的已验证部署状态、聚合趋势。P2：部署历史、多环境对比、告警、细粒度权限与受控运维操作。分期是建议，需你确认业务优先级。

## 6. Overview 指标与统计口径

“已安装店铺”定义为在所选环境、统计时点，应用本地安装记录处于 installed 的去重 store ID 数；仅有当前会话不能证明历史安装数。“有效活动”定义为同一时点本应用活动记录按商家端规则计算为 Active 的数量，不能计入原型样本。“最近错误数”建议为过去 24 小时应用侧去重错误事件数，按发生时间及环境过滤，展示错误事件而非失败商家数。所有指标须显示环境、时区、时间范围、最近成功同步时间和数据延迟；历史趋势须说明是否基于事件快照，不能由当前状态反推。

## 7. Stores 商家管理

列表至少支持 store ID/名称/域名搜索、安装状态筛选、最近授权/同步时间排序和分页。详情显示商家身份、安装/卸载时间线、授权 scope、关联活动摘要及最近异常。token、secret、Webhook 原文和敏感个人数据不得出现在响应、导出或页面中。域名变更、重装、Webhook 重试/乱序、卸载后历史记录保留均须定义规则；当前安装事件存储尚不存在。

## 8. Bundles 活动管理

首版仅查看本应用创建的活动，按稳定 store ID 过滤。列表候选字段：活动 ID、店铺、名称、类型、派生状态、计划时间、更新时间。详情候选字段：活动配置摘要、覆盖范围摘要、折扣档位、发布状态。真实模型尚未存在，字段以商家端最终持久化模型为准。跨店同名活动不得混淆；已删除活动是否留审计快照待确认。SHOPLINE 原生折扣列表是否可用于补充状态需单独验证，不能作为默认来源。

## 9. Logs 日志管理

日志分 API、Webhook、业务校验和后台审计；每条至少含时间、环境、类型、严重度、关联 store ID（如有）、trace ID 和脱敏摘要。查询支持时间范围、类型、级别、店铺及分页。默认隐藏原始请求/响应；保留期、采样、访问权限和敏感字段屏蔽待确认。当前 `console.log` 不是可靠、可检索的数据源。

## 10. Monitoring 运行监控

候选观测项：服务探针、授权回调失败、Webhook 处理失败/重试、活动发布失败、Function 运行异常（能力待验证）。状态以最后观测时间和阈值计算；无指标时显示“未接入/未知”。MVP 可仅展示已采集错误摘要，完整健康页属 P1。

## 11. Deployments / Extensions

展示应用服务、Product Discount Function、Theme App Extension 的版本、目标环境、发布时间、发布结果和证据链接；来源优先为 CI/CD 发布记录，SHOPLINE 可查询接口待验证。部署状态不等于商家主题已启用 Extension；商家级启用状态如需展示，必须另行验证可获得性。部署管理与回滚不在 MVP。

## 12. Admin Authentication

管理员需独立于 SHOPLINE 商家 OAuth 的登录入口。已确认暂时没有公司 SSO，需独立管理员账号；MFA、邀请/停用、会话寿命、紧急访问流程仍须在技术方案中明确。管理 API 必须在服务端验证身份与 RBAC；CSRF、会话撤销、速率限制及失败登录审计列为验收条件。不能直接读取 `shopline_sessions` 的 accessToken 供浏览器使用。

## 13. 数据来源及 API 依赖

已确认的本地来源：SQLite 商家会话表、安装/卸载 Webhook 处理、前端样本数据、Function/Theme Extension 源码。会话表只证明当前授权会话，不能独立提供完整商家名册；前端样本不能用于真实统计。待建立的应用来源：安装生命周期记录、活动持久化、结构化事件/审计记录、部署记录。待验证的外部来源：SHOPLINE 店铺身份/名称、原生优惠状态、Function 运行指标、商家级 Extension 启用状态；本文件不假定接口存在或现有 scope 足够。

## 14. 数据安全与商家隔离

所有跨店查询需先通过管理员角色，再以稳定 store ID 限定对象。服务端记录管理员与访问对象；生产与测试数据不混查。列表采用最小字段集，详情按需读取。凭证加密存储和密钥轮换属于架构阶段评估；当前会话表含 accessToken，必须保护读取路径。导出、批量访问、原始日志查看默认关闭，待单独确认。卸载后保留期限与数据删除义务须与平台要求核对。

## 15. 页面与导航结构（信息需求，非 UI 设计）

候选一级导航：Overview、Stores、Bundles、Logs、Monitoring、Deployments、Admin/Audit。MVP 先提供 Overview、Stores、Bundles、Errors、Audit；Monitoring/Deployments 待数据源就绪后开放。无权限的导航项不可进入，对深链也须服务端拒绝。具体布局、组件和视觉规范留待阶段 3。

## 16. 典型操作流程

1. 管理员登录 → 查看 Overview 的错误数和数据时间 → 进入错误记录 → 按 store ID 打开商家详情 → 查看相关活动与事件。
2. 支持人员输入店铺域名 → 在匹配结果中确认稳定 store ID → 查看安装/授权与最近异常 → 复制脱敏 trace ID 交给工程排查。
3. Owner 查看审计记录 → 确认谁在何时查看过某店敏感详情或尝试导出。

## 17. 异常及边界场景

未安装/已卸载/重装；Webhooks 重复、乱序、延迟或遗漏；店铺改域名；活动跨店同名；活动已删除；真实活动数据源尚未上线；部分聚合来源失败；时区与夏令时；日志脱敏失败；无权限深链；管理员停用后仍持有旧会话；部署记录与实际环境不一致。每种情况应显示明确状态、来源和最后更新时间，且不得回退显示 mock 数值。

## 18. 非功能需求

管理 API 采用服务端分页与查询上限；列表响应时间目标、允许的数据延迟和目标店铺规模待确认。关键页面需可键盘操作、具有可读的错误/空/加载状态。审计事件须不可由普通管理员删除。测试环境使用隔离数据。日志与指标留存期限、备份恢复目标、可用性目标须在技术设计前确认。

## 19. 验收原则

MVP 验收至少包括：未授权与越权访问测试、跨店对象 ID 篡改测试、安装/卸载/重装状态测试、真实活动与商家端记录对照、指标口径核对、日志脱敏检查、审计记录完整性、分页筛选、源不可用状态及无 mock 数据检查。任何未接入真实数据的模块标 `BLOCKED` 或 `NOT_TESTED`，不能标 `PASS`。

## 20. 不支持与后续扩展

MVP 不支持：从后台创建/编辑/删除活动、查看明文 token、代商家执行敏感操作、跨平台所有优惠查询、商家账单/收入分析、自动回滚、以示例数据冒充真实数据。后续可考虑经过审批的受控运维操作、告警规则、部署对比、按商家维度的性能趋势、只读数据导出，但均需重新评估权限与数据来源。

## 21. 待你决策的问题

1. 首版最重要的目标是客服排障、运营观察，还是工程运行监控？这决定 MVP 的排序。
2. 已确认暂无公司 SSO，需独立管理员账号；具体可访问人员、MFA 和账号恢复规则待确认。
3. 首版是否接受 Bundles 页面在商家端真实活动持久化上线前显示“未接入”，还是必须把活动持久化作为管理后台的前置项目？
4. 是否需要保留卸载商家的历史记录？保留多久，哪些角色能查看？
5. 生产/测试环境是否都纳入后台？默认进入哪个环境？
6. 首版日志与审计保留期，以及是否允许任何形式的导出？

这些问题的答案会改变需求范围。本文中的角色、优先级、统计口径和页面集合均是建议，未获确认。
