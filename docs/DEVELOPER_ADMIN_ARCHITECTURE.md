# Developer Admin Console 技术架构（阶段 2，已确认）

更新日期：2026-10-14。阶段 2 技术方案已获确认；文中尚未指定的运营参数仍待确定。

## 目标和现状

后台供内部人员跨店排障及观察本应用状态，首版业务数据只读。现有商家服务是 Express，SHOPLINE OAuth 会话存于本地 SQLite `shopline_sessions`；活动仍是 React 原型状态，未持久化。现有 `/api/*` 校验商家会话，不能作为管理员鉴权。用户已确认暂无公司 SSO，需独立管理员账号。SHOPLINE 原生折扣、Function 运行指标和商家级 Theme Extension 启用状态的数据接口均待验证。

## 部署方案比较

| 维度 | A：同一 Express 服务、独立后台路由 | B：独立管理服务 + 商家服务内部只读 API |
| --- | --- | --- |
| 部署 | 共用进程与发布周期 | 独立域名、进程、会话和发布周期 |
| 数据 | 同进程读取业务库 | 商家服务拥有业务数据；管理服务只经受保护的内部接口读取 |
| 优点 | 初期部署成本低 | 认证和凭证边界清晰；管理端不能直接读取商家 token；故障隔离较好 |
| 代价 | Cookie、路由和权限隔离脆弱；发布影响商家服务 | 需要第二个部署单元和服务间鉴权；业务数据模型仍需先补齐 |
| 适用 | 短期单机内部试运行 | 长期运行、需要跨店访问和独立审计的后台 |

**推荐 B。** 商家应用保留 SHOPLINE 授权、Webhook、活动写入与状态计算；管理服务负责独立身份、RBAC、只读查询编排和审计。管理端不重写 Bundle 业务引擎。若暂时只有单机环境，可先在一个仓库内实现相同的模块/接口边界，但正式上线需独立域名与会话并验证进程隔离。方案 A 不得直接沿用商家端 `validateAuthentication()`。

```text
管理员浏览器 -> 管理服务（账号/MFA、会话、RBAC、审计）
                         |
                         | 私有网络 + 短时服务凭据
                         v
                  商家应用内部只读 API -> 业务数据库
                         |
                         +-> SHOPLINE OAuth / Webhook / 活动业务
```

## 数据库与复用

商家应用是 `stores`、安装周期、活动及应用错误事件的权威写入方。当前 SQLite 会话表只证明会话，不是商家名册，且含 accessToken；管理服务不能连接或复制它。开发环境可继续使用现有 SQLite 会话存储，但它不能作为两个部署共享的文件数据库。正式多实例部署前，建议把新增业务数据放到有事务、备份和并发能力的托管关系数据库，并评估会话迁移；若坚持单实例 SQLite，必须用负载、锁、备份及恢复演练证明满足目标。管理账号、会话和审计放独立逻辑库或至少独立 schema/凭据，管理服务数据库凭据无权读商家 token。

真实活动持久化是活动查询的前置工作。若该工作尚未完成，Bundles API 返回 `SOURCE_UNAVAILABLE`，页面显示“未接入”，不得从 `campaignData` 生成统计。商家服务按同一业务规则派生活动状态，管理服务只读取投影。

## 管理员身份与权限

仅 Owner 可邀请内部账号；无公开注册。密码由成熟库以 Argon2id 加盐哈希；所有管理员建议强制 WebAuthn 或 TOTP MFA，恢复码一次性使用且只存哈希。首次 Owner 通过一次性、短时、离线引导创建；生产环境不保留 bootstrap 密钥。服务端会话使用 Secure、HttpOnly、SameSite=Lax Cookie，登录和权限变更后轮换会话 ID，支持立即撤销，并分别限制空闲和绝对有效期。状态变更请求验证 CSRF；登录、恢复及邀请限速。账号恢复责任人和具体 MFA 方式待确认。

候选 RBAC：Viewer 可看概览及商家/活动基础字段；Operator 另可看脱敏错误和诊断；Owner 另可看审计并管理管理员账号。业务数据均只读；Owner 也不能读取 SHOPLINE token。每个 API 在服务端校验角色和环境，详情需校验 `bundle.storeId` 与目标店铺一致；不能靠隐藏前端导航实现授权。内部服务身份只能访问列明的只读接口。

## 跨店查询与统计

`storeId` 必须来自经过验证的 SHOPLINE 授权/事件中的稳定标识；现有 SDK 是否提供该值待查，不能把可变 handle 当永久主键。安装/卸载事件幂等入库，记录事件和接收时间；重装产生新周期，店铺数按稳定 ID 去重。列表由服务端做白名单筛选、排序、分页和上限。Overview 由商家服务按环境/时间范围聚合，返回每项口径、`asOf` 和 `sourceStatus`；来源失效返回 unavailable，不能回退为 mock 或过期“正常”值。

## 日志、监控和部署

MVP 仅采集结构化、脱敏错误：时间、环境、类型、严重度、store ID（如有）、trace ID、错误码和摘要。默认不记录请求/响应正文、token、Cookie 或个人资料。现有 Webhook 完整 payload 日志及认证结果响应回显须在后台接入前整改。管理员登录、敏感详情访问、角色变更和失败尝试写独立审计；审计写入失败时敏感管理操作失败关闭。保留期、采样、备份和清理策略待确认。

P1 的健康状态依据明确探针、阈值及最后观测时间；无指标显示 unknown。CI/CD 为服务、Function、Theme Extension 记录不可变版本、环境、发布时间及结果；“已发布”不等于“商家已启用”。SHOPLINE 平台指标与启用状态接口须实证验证后才接入。

## 环境、安全与失败处理

管理服务用独立 HTTPS 域名，不嵌入商家 iframe。生产、预发布和开发的账号、Cookie、服务凭据与数据隔离；页面及 API 始终明确环境。服务凭据放密钥管理器并轮换；内部接口优先私网，若无私网则需双向 TLS 或短时签名凭据及来源限制。内部 API 超时、部分聚合失败或数据源缺失时返回可识别错误和最后成功时间，不静默给出零值。所有列表与详情仅返回字段白名单。

## 验证范围与实施顺序

先验证稳定 store ID、安装事件和活动持久化，再实现内部只读接口，最后接入管理员身份和页面。测试覆盖商家 Cookie 访问后台 401、角色越权 403、跨店对象 404、重复/乱序 Webhook、卸载重装、会话撤销、MFA 恢复、日志脱敏、服务凭据失效、审计写入失败和数据源不可用。Function/主题状态在能力验证前标 unsupported。
