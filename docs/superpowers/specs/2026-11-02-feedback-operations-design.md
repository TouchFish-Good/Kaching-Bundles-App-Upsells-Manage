# 需求与建议运营设计

## 目标

为唯一 Owner 提供一个“需求与建议”运营工作台，管理商家应用中真实保存的建议和评论。Owner 可以检索建议、查看匿名来源、改变建议状态、发布官方回复、拒绝公开显示建议，以及删除不当评论。

管理后台继续运行在 Cloudflare Worker。商家应用的 App D1 是建议、评论、状态历史和商家撤回记录的唯一权威来源；管理后台的 Admin D1 只保存自身会话和操作审计，不复制反馈业务数据。

## 已有能力

商家应用已经保存下列真实数据：

- 建议：标题、内容、提交店铺 ID、`handle` 快照、匿名标记、创建/更新时间、状态、可见性、撤回原因。
- 评论：评论店铺 ID、`handle` 快照、匿名标记、内容和创建时间。
- 状态历史、商家撤回审计和“多件折扣”官方回复。
- 使用 HMAC 时间戳和 nonce 签名的内部状态更新及官方回复接口。

商家端匿名仅隐藏公开身份；Owner 在管理后台必须始终看到原始 `handle` 和匿名标记。

## 业务规则

### 建议状态

正常业务状态保持为：`pending`（待审核）、`approved`（已批准）、`in_progress`（开发中）、`released`（已上线）、`rejected`（已拒绝）。

管理后台额外展示 `拒绝显示`。它不是商家公开状态枚举中的新值，而是以下持久化组合：

- `status = rejected`
- `visibility = hidden`
- `hidden_reason = owner_rejected_display`

这样既能保留“拒绝”的业务含义，也不会把本应对商家隐藏的状态暴露给商家端。商家公共列表、提交商家自己的列表、建议详情、投票和评论均不得返回这一类记录。Owner 后台可以查询、查看内容和按“拒绝显示”筛选。

普通“已拒绝”沿用现有公开语义，可被商家看到；两者在管理后台必须有不同的中文标签。

### 评论

评论不进入待审核队列。Owner 可删除任意评论：

- 删除是软删除，商家端立即不返回内容。
- 数据库保留评论 ID、作者店铺、原内容、删除时间、删除原因和操作方，支持审计。
- 管理后台详情将已删除评论标为“已删除”，只对 Owner 保留原始内容访问。
- 不提供恢复操作，本期也不新增商家侧举报入口。

### 官方回复

Owner 在已公开的建议详情中可发布回复。商家应用服务端强制写入固定身份：`多件折扣`、`isOfficial: true`；商家前台使用现有官方头像和官方标签。前端提交的任意伪造身份字段均被忽略。

### 撤回记录与异常内容

商家主动撤回的建议继续由 `hidden_reason = withdrawn_by_submitter` 标识。Owner 可以检索该记录并查看撤回时间与原始提交信息，但不可再转换状态或公开。

“拒绝显示”用于 Owner 发现的垃圾信息、敏感内容、恶意内容或其他不适合公开的建议。每次处理必须写入商家应用的反馈审计表和 Admin D1 的 Owner 审计表。

## 管理后台界面

新增主导航项“需求与建议”。默认视图为待审核队列。

列表字段：

- 标题和内容摘要
- 真实商家 `handle` 与稳定店铺 ID
- `匿名发布` 标记
- 当前状态或 `拒绝显示` / `已撤回` 生命周期标签
- 创建时间、更新时间、投票数、评论数和官方回复标记

筛选与检索：

- 标题和内容关键词
- 状态/可见性：全部、待审核、已批准、开发中、已上线、已拒绝、拒绝显示、已撤回
- 商家 `handle` 或稳定店铺 ID
- 创建日期起止范围
- 游标或 offset 分页，每页最多 100 条

详情页或侧栏显示完整内容、真实作者、匿名标记、状态历史、商家撤回记录、官方回复和评论。建议操作使用明确的命令按钮：批准、拒绝、标记开发中、标记已上线、拒绝显示。评论操作仅提供删除图标按钮与确认对话框。

所有管理后台可见文案使用中文；按钮和写操作有加载、成功和失败状态，不使用模拟数据。

## 跨 Worker 内部契约

Admin Worker 只能通过现有 `MERCHANT_APP` Service Binding 调用商家 Worker，沿用共享 `ADMIN_INTERNAL_SECRET`、请求方法、规范路径、时间戳和 nonce HMAC 签名。不得向 Admin Worker 绑定商家 App D1。

商家 Worker 增加以下受签名保护接口：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/internal/admin-read/v1/feedback` | Owner 列表与筛选数据 |
| GET | `/internal/admin-read/v1/feedback/:id` | Owner 详情、状态历史和评论 |
| PATCH | `/internal/admin/v1/feedback/:id/status` | 正常状态变更或拒绝显示 |
| POST | `/internal/admin/v1/feedback/:id/replies` | 发布固定官方身份回复 |
| DELETE | `/internal/admin/v1/feedback/:id/comments/:commentId` | 软删除评论 |

Admin Worker 增加对应的 Owner 鉴权 API。所有修改都验证 CSRF、验证请求体和 ID 格式，并记录 Owner 审计。读取响应经过白名单投影：不返回 OAuth token、内部签名、原始请求头或不属于反馈运营的数据。

## 数据库变更

商家 App D1 新增迁移以扩展评论可见性和删除审计字段，例如：

- `feedback_comments.visibility`，默认 `public`
- `feedback_comments.deleted_at`
- `feedback_comments.deleted_by_admin_id`
- `feedback_comments.deletion_reason`

既有评论默认公开。商家端读取评论时只返回 `visibility = public`；内部 Owner 读取可返回删除元数据与原文。建议不创建新的建议状态枚举；拒绝显示使用现有可见性字段及受限原因值。

## 安全与一致性

- 管理端永远看到匿名建议和评论的实际 `handle`，商家端永远不应通过内部字段获得其他匿名作者身份。
- 任何隐藏/删除失败时不得返回成功；业务写入、商家应用审计和必要的 Admin 审计必须作为可观测的失败处理。
- 商家撤回、Owner 拒绝显示和评论删除均不可通过普通商家 API 恢复或重新公开。
- 管理 Worker 对写响应重新投影，只返回界面需要的字段。
- 列表和详情读取、状态改变、回复、评论删除均验证签名重放防护。

## 验收标准

1. 待审核队列展示真实 `handle`、匿名标记、标题、内容摘要和创建时间。
2. Owner 能按关键词、状态、商家和日期筛选；商家不可调用这些 Owner 数据接口。
3. Owner 可成功执行批准、拒绝、开发中、已上线和拒绝显示；每次都有两端审计记录。
4. 被“拒绝显示”的建议对提交商家、其他商家、投票、评论和公开列表均不可见，但 Owner 可检索。
5. 商家主动撤回记录可被 Owner 检索，且不能被重新公开。
6. Owner 回复在商家端只显示“多件折扣”、官方标签和现有官方头像。
7. Owner 删除评论后，商家端不再看到该评论；Owner 详情可看到删除状态与审计元数据。
8. 覆盖 HMAC 签名、重放防护、CSRF、匿名身份不泄漏、无效筛选、状态转移、删除评论和数据源错误的自动化测试。
9. 完成管理后台桌面与移动端的实际截图验收，不以测试夹具作为真实商家数据验收。
